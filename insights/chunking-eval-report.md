# 청킹 실험 인사이트 — 민지 (2026-11-25)

> **한 줄 요약 (새 데이터 S2)**
> - **검색은 800자가 가장 좋습니다.** 정답 섹션이 상위 5개에 드는 비율이 0.842로 가장 높습니다.
> - **답의 완성도는 1600자가 조금 더 좋습니다.** 대신 입력 토큰이 800자보다 50% 정도 많습니다.
> - **앞 문장 하나를 겹치는 방식은 효과가 뚜렷하지 않습니다.** 크기에 따라 오르기도 하고 내리기도 하며, 차이가 1~3문항 수준입니다.
> - **실패는 대부분 생성 단계입니다.** 정답 근거를 받고도 거절하거나 핵심 사실을 빠뜨린 경우가 8~12문항이고, 그다음이 정답 조각이 6~20위에 있어 모델에 못 들어간 경우(순위 밀림)입니다. 청크 크기보다 상위 k · 재정렬 · 질문 나누기 쪽이 더 큰 변수로 보입니다.
>
> **어젯밤 handoff 실험(2부)의 결론**은 그대로입니다. 한국어 질문은 영어로 바꿔 검색해야 하고, 인물 · 세계관 문서는 색인에 넣는 게 낫습니다.

이 문서는 두 부분입니다.
- **1부:** 영민님 새 데이터로 청크 크기 3개 × 겹치기 2개 = 6개를 비교한 실험 (S2, 오늘)
- **2부:** 학용님이 넘겨준(handoff) 이전 데이터로 청크 방식 · 문서 범위를 비교한 실험 (어젯밤). R0 = 원래 청크 그대로, R1 = 800자로 다시 자름, R2 = R1 + 인물 · 세계관 문서

두 부분은 데이터 · 자르는 방법 · 번역기 · 발췌 대조 규칙이 달라서 **숫자를 서로 바로 비교하면 안 됩니다.**

## 0. 처음 보는 분을 위한 설명

### 이 실험이 묻는 것
우리 챗봇은 영어 위키 문서에서 근거를 찾아 한국어로 답합니다. 문서는 너무 길어서 통째로 넣을 수 없으니 **조각(청크)으로 잘라 저장**해 두고, 질문이 오면 비슷한 조각 몇 개를 꺼내 모델에게 보여 줍니다.

이때 **조각을 얼마나 크게 자를지**, **조각끼리 조금 겹치게 할지**에 따라 찾는 정확도와 답의 질이 달라집니다. 이 실험은 그 둘을 바꿔 가며 어느 쪽이 나은지 잽니다.

### 확인한 것과 안 한 것
- **모델 비교 실험이 아닙니다.** 임베딩 모델 · 답 모델 · 채점 모델 · 검색 방식은 모든 실행에서 똑같고, **청크를 자르는 방법만** 바꿨습니다.
- **검색만이 아니라 최종 답까지 봤습니다.** 실행마다 질문 20개를 실제로 모델에 보내 한국어 답을 받았고, 그 답이 맞는지까지 채점했습니다. 그래서 "청킹을 바꾸면 검색 결과와 최종 답이 얼마나 달라지나"를 함께 볼 수 있습니다.
- **답 채점은 LLM이 했습니다.** 채점 모델이 평가셋의 "채점 핵심 사실"(문항마다 3~4개)을 하나씩 대조해 맞음/틀림과 이유 한 줄을 남깁니다.
  - 예: 400자 + 겹치기 실행의 Q001 "타임 스톤이 뭐야?" → 사실 3개 중 2개 맞음(`1,1,0`), 메모 "…아이 오브 아가모토에 보관된다는 내용은 없습니다." 같은 문항이 800자 실행에서는 3개 모두 맞았습니다.
  - 어디에 남나: 실행마다 `results/<실행 이름>.scores.json`의 문항별 `judge` 칸(`facts` = 사실별 맞음/틀림, `note` = 이유)과, 엑셀로 열 수 있는 `results/<실행 이름>.runs.csv`의 `judge_facts` · `judge_note` 열. 모델이 실제로 쓴 답 원문은 `results/<실행 이름>.jsonl`의 `answer`에 있습니다.
- **사람 검토는 일부만 했습니다.** 결과가 이상한 문항 8개(Q001 · Q004 · Q009 · Q040 · Q041 · Q052 · T001 · T003)는 답과 채점 메모를 직접 읽어 확인했고, 채점 메모가 답 내용과 맞았습니다. 나머지 답(20문항 × 6번)은 사람이 다 읽지 않았습니다. 최종 평가 전에는 사람 검토가 필요합니다.
- **실행은 한 번씩입니다.** 다시 돌리면 답이 1~2문항 바뀔 수 있습니다.

### 질문 하나가 처리되는 순서
```
한국어 질문 "타임 스톤이 뭐야?"
  ① 영어 검색어로 바꾸기      → "What is the Time Stone?"   (팀 번역 도구)
  ② 비슷한 조각 20개 찾기      → 벡터 검색 (뜻이 비슷한 글을 숫자로 비교해서 찾음)
  ③ 그중 상위 5개만 모델에 주기
  ④ 모델이 한국어로 답하고, 근거로 쓴 조각 번호를 [1] 처럼 붙임 (근거가 없으면 "찾을 수 없음")
  ⑤ 채점: 정답 근거를 찾았나(검색 점수) · 답이 맞나(답 점수)
```

### 용어
| 용어 | 뜻 |
|---|---|
| **청크** | 문서를 자른 조각 하나 |
| **최대 글자 수 (400 · 800 · 1600)** | 조각 하나가 넘으면 안 되는 길이. 실제 조각은 문단 · 문장 끝에서 끊기 때문에 보통 이보다 짧음 |
| **겹치기** | 앞 조각의 끝부분을 다음 조각 앞에 한 번 더 붙이는 것. 경계에서 앞뒤 내용이 끊기지 않게 하려는 것 |
| **섹션** | 위키 문서 안의 한 절 (예: 어벤져스: 엔드게임 문서의 "Plot" 절) |
| **정답 섹션** | 평가셋에 "이 질문의 근거는 이 문서의 이 절"이라고 적어 둔 곳 |
| **섹션 Hit@5** | 상위 5개 조각 중 하나라도 정답 섹션에서 나왔으면 1. 19문항의 평균 |
| **발췌 Hit@5** | 상위 5개 조각 안에 평가셋에 적힌 **정답 근거 문장**이 그대로 들어 있으면 1. 섹션 Hit보다 엄격함 |
| **재현율@5** | 근거가 여러 개인 문항에서, 그중 몇 %를 상위 5개 안에서 찾았나 |
| **정답 충족** | 채점 모델(LLM)이 보기에 답이 핵심 사실을 **전부** 담았으면 1 |
| **핵심 사실 맞춘 비율** | 핵심 사실 3~4개 중 몇 개를 맞혔나의 평균. 정답 충족보다 차이가 잘 보임 |
| **거절** | 모델이 "근거에서 찾을 수 없습니다"라고 답한 경우. 답할 수 있는 문항에서 거절하면 오답 |
| **입력 토큰** | 모델에 넣은 글의 양. 많을수록 비용이 듦 |
| **임베딩** | 글을 숫자 묶음(벡터)으로 바꾼 것. 벡터 검색은 이 숫자끼리 얼마나 비슷한지로 찾음 |
| **상위 k** | 검색 결과 중 모델에 넣는 개수. 이 실험은 k = 5 |
| **인용이 정답 섹션** | 답에서 [번호]로 인용한 조각이 정답 섹션에서 나온 비율 |
| **A · B · C · C+ · D 구성** | 팀 검색 설계의 단계. A = 벡터 검색만, B = + BM25(키워드 검색), C = + 재정렬(검색 결과를 다른 모델로 다시 순위 매김), C+ = + 질문 전체 영어 번역, D = 가공 색인 |

> **숫자 읽을 때 주의:** 답할 수 있는 문항이 19개라 **1문항 = 0.053**입니다. 0.05 정도 차이는 우연일 수 있습니다.

# 1부. 새 데이터 S2 — 청크 크기 × 겹치기

## 1-1. 무엇을 바꿨나

청크 크기(최대 글자 수)와 겹치기만 바꿨습니다. 나머지는 6개 실행이 모두 같습니다.

| 실행 | 최대 글자 수 | 겹치기 | 청크 수 | 청크 길이 중앙값 |
|---|---|---|---|---|
| S2-400 | 400 | 없음 | 12,219 | 309 |
| S2-400-o1s | 400 | 앞 문장 1개 | 12,219 | (309 + 겹친 문장) |
| **S2-800** | 800 | 없음 | 6,627 | 592 |
| **S2-800-o1s** | 800 | 앞 문장 1개 | 6,627 | (592 + 겹친 문장) |
| S2-1600 | 1600 | 없음 | 3,823 | 1,020 |
| S2-1600-o1s | 1600 | 앞 문장 1개 | 3,823 | (1,020 + 겹친 문장) |

이름 읽는 법: **S2** = 새 데이터 실험, **o1s** = overlap 1 sentence(앞 문장 1개 겹치기), **c2** = 이번 청커 버전, 결과 파일 끝의 **-tr** = 팀 번역 검색어.

- 400 · 800 · 1600은 **넘으면 안 되는 상한**입니다. 실제로 자르는 위치는 아래 순서로 정합니다.
- 겹치기를 켜도 **자르는 위치는 똑같고**, 앞 조각의 마지막 문장만 다음 조각 앞에 붙습니다. 그래서 겹치기 효과만 따로 볼 수 있습니다.

### 자르는 방법 (청커 c2)

LangChain `RecursiveCharacterTextSplitter`와 같은 "큰 단위 → 작은 단위" 방식이지만, **문장 단계를 넣고 약어를 구분하도록** 직접 짰습니다 (`src/experiments/chunking/chunker.py`).

1. **원문 섹션 하나씩 따로** 자릅니다. 서로 다른 섹션이 한 청크에 섞이지 않습니다.
2. 섹션이 상한 안에 들어가면 통째로 한 청크로 둡니다.
3. 넘으면 **문단**을 차례로 담다가, 다음 문단을 넣으면 넘칠 때 끊습니다.
4. 문단 하나가 넘으면 **문장**으로 나눕니다. `Dr.` · `S.H.I.E.L.D.` · `Vol.` · `Jan.` · `Bros.` 같은 약어의 점은 문장 끝으로 보지 않습니다.
5. 문장 하나가 상한보다 길 때만 문장 안에서 자릅니다. 이때도 `;` → `,` → 띄어쓰기 순으로 덜 어색한 곳을 고릅니다.
6. 청크 앞에 `[작품 제목 · 섹션]` 머리말을 붙여 같이 임베딩합니다.

**Recursive를 그대로 쓰지 않은 이유**
- Recursive의 기본 자르기 순서(문단 → 줄 → 띄어쓰기)에는 문장 단계가 없어서, 문단이 길면 문장 한가운데서 자릅니다.
- `". "`를 자르는 기준에 넣으면 이번엔 약어에서 잘못 자릅니다. 예전 c1 방식에서는 경계의 약 9%가 이렇게 잘렸습니다.
- Recursive의 겹치기(`chunk_overlap`)는 글자 수 기준이라, 다음 청크가 문장 중간에서 시작합니다.
- 다만 **문장 경계를 지키는 것이 점수를 얼마나 올리는지는 아직 비교하지 않았습니다.** Recursive 기준선 실행이 남은 숙제입니다.

**겹치기(o1s)**
- 앞 조각의 **마지막 한 문장을 통째로** 다음 조각 앞에 붙입니다. 글자 수로 자르지 않아서 문장 중간부터 시작하는 일이 없습니다.
- 그 문장이 상한의 절반보다 길거나, 원문에서 진짜 문장 끝 다음에 시작하는 완전한 문장이 아니면 붙이지 않습니다.

| 크기 | 겹치기가 실제로 붙은 경계 | 붙은 길이 (중앙값) | 상한 대비 (붙은 길이 ÷ 최대 글자 수) |
|---|---|---|---|
| 400 | 75% (7,198 / 9,605) | 120자 | 약 30% |
| 800 | 93% (3,729 / 4,013) | 128자 | 약 16% |
| 1600 | 92% (1,111 / 1,209) | 131자 | 약 8% |

→ 실무에서 흔히 쓰는 10~20%와 비교하면 **400자에는 많고, 1600자에는 적습니다.**

**잘 잘렸는지 검사** (문단 안에서 생긴 경계를 모두 조사)

| 크기 | 문장 끝에서 자름 | 약어 · 이니셜 뒤 | 문장 안에서 억지로 자름 | 문장 중간(약어 뒤) 잘못 자름 |
|---|---|---|---|---|
| 400 | 6,654 | 13 | 388 | 6 |
| 800 | 1,874 | 7 | 124 | 2 |
| 1600 | 111 | 6 | 49 | 0 |

남은 6 · 2곳은 위키 표가 깨진 찌꺼기 글(colspan 등)이라 문장 자체가 없는 경우입니다.

## 1-5. 해석

### ① 검색은 800자가 가장 좋다
- 섹션 Hit@5가 **400 → 800에서 0.684 → 0.842**로 오르고, **1600에서 0.789**로 다시 내려갑니다.
- 400자 조각은 담긴 내용이 적어서, 정답 섹션의 조각이라도 질문 전체와 뜻이 덜 비슷하게 나옵니다. 그 자리를 다른 문서 조각이 차지합니다(순위 밀림 4~5문항).
- 1600자는 한 조각에 여러 사건이 섞이고, 크기가 커진 다른 문서 조각들이 질문과 더 비슷하게 나와 앞으로 올라옵니다. Q009(윈터 솔저)는 800에서 5위로 겨우 상위 5개에 들었는데, 1600에서는 7위로 밀려 모델에 들어가지 못했습니다.

### ② 답의 완성도는 큰 청크가 조금 낫다 (토큰 비용과 맞바꿈)
- 정답 충족 **3 → 4 → 5문항**, 핵심 사실 맞춘 비율 **0.33 → 0.43 → 0.49**로, 크기가 클수록 오릅니다.
- 1600은 모델이 읽는 글이 많아서(맥락 5,968자) **거절이 2문항으로 가장 적습니다.** 근거를 받았는데 "찾을 수 없음"이라고 하는 경우가 줄어듭니다.
- 대신 입력 토큰이 **800 대비 +53%**(1,110 → 1,697)입니다. 응답 시간은 생성이 대부분이라 거의 같습니다.

### ③ 앞 문장 하나 겹치기는 효과가 뚜렷하지 않다
- **800:** 발췌 Hit 0.684 → 0.737, 사실 비율 0.425 → 0.460으로 조금 오릅니다.
- **400:** 발췌 Hit 0.526 → 0.368로 오히려 떨어집니다. 겹친 문장이 상한 400자의 30%(실제 조각 길이 기준으로는 약 40%)나 돼서, 같은 문장이 두 청크에 들어가 상위 5개 자리를 나눠 먹는 것으로 보입니다.
- **1600:** 섹션 Hit 0.789 → 0.684로 떨어지고 거절이 2 → 5로 늘어납니다. 그런데 겹친 문장은 상한의 8%뿐이라, 겹치기 탓이라기보다 **한 번씩만 돌린 생성의 흔들림**일 가능성이 큽니다.
- 차이가 모두 1~3문항(0.05~0.16)이라 **이 실험만으로는 "겹치기가 좋다/나쁘다"를 말할 수 없습니다.**

### ④ 중수 · 고수 0점은 청크 크기 문제가 아니다
- 중수 · 고수 문항(예: Q040 "울트론을 만든 이유가 시빌 워에 어떻게 이어지나", Q052 "소코비아 협정")은 **여러 작품을 엮어야 하는 질문**입니다.
- 검색은 정답 섹션 일부를 찾지만(Q052는 800에서 4위), 핵심 사실 3~4개를 모두 채우려면 서로 다른 문서의 근거가 함께 필요합니다. 상위 5개로는 부족합니다.
- → 청크 크기보다 **상위 k 늘리기, 재정렬(C), 질문을 작품별로 나눠 검색하기**를 봐야 합니다.

### ⑤ 팀에 같이 정할 것 · 제안
- **기본 청크 크기는 800자를 제안합니다.** 검색 지표가 가장 좋고 토큰도 중간입니다. 답 완성도를 더 원하면 1600도 후보입니다.
- 겹치기는 결론을 내리려면 **크기 대비 15% 정도를 문장 단위로 겹치는 방식**을 한 번 더 돌려 봐야 합니다. 지금 방식은 1600에서 너무 짧습니다.
- 평가셋 정답 섹션을 넓힐지 명석님과 정할 일입니다 (아래 1-7의 3번).

## 1-7. 한계 · 주의

1. **문항이 19개라 1문항 = 0.053입니다.** 실행도 한 번씩만 했습니다. 생성 · 채점은 매번 조금씩 달라서 **0.05 차이는 믿기 어렵습니다.** 같은 크기에서 겹치기만 다른 두 실행이 Q001에서 정답/오답으로 갈린 것도 이 흔들림으로 봅니다. 검색 지표가 상대적으로 더 믿을 만합니다.
2. **채점이 엄격합니다.** 정답 충족은 핵심 사실을 전부 맞혀야 1입니다. Q001(타임 스톤)은 "아이 오브 아가모토에 보관" 한 마디가 빠져 오답이 됐습니다. 그래서 "핵심 사실 맞춘 비율"을 같이 실었습니다. 채점은 LLM 판정이고 사람이 검토하지 않았습니다.
3. **평가셋 정답 섹션이 좁은 문항이 있습니다.**
   - Q004(와칸다): 세계관 문서의 와칸다 섹션이 6개 실행 모두 상위 1~5위를 전부 차지하지만, 정답이 블랙 팬서 줄거리로만 적혀 있어 6개 모두 "순위 밀림"입니다.
   - T001: 타노스 인물 문서가 상위를 차지하고 답도 맞는 방향입니다. 정답은 엔드게임 줄거리로만 적혀 있습니다.

4. **"A + 팀 번역" 조건입니다** (1-2 참고). 번역 없는 A 단계 숫자가 아닙니다.
5. 위키 표가 깨진 찌꺼기 글(colspan 등)이 일부 청크에 들어 있습니다. 문장이 없어서 경계 검사에서도 걸러지지 않습니다.
6. 작품 문서의 **lead 섹션**은 색인에 넣지 않았습니다. Q004 · Q056은 근거 일부가 lead입니다.
7. **Recursive 분할기 기준선과 비교하지 않았습니다.** 문장 경계를 지키는 것의 효과는 아직 확인되지 않았습니다.

## 2-4. 해석

### ① 한국어 질문은 영어로 바꿔서 검색해야 한다 (R0-ko → R0-en)
- 한국어로 검색하면 유사도가 0.2대로 낮고 엉뚱한 작품(Echo, Daily Bugle)이 올라와서 **19문항 중 18문항을 거절**했습니다.
- 영어로 바꾸자 섹션 Hit@5가 **0.105 → 0.579**, 정답 충족이 **0 → 4문항**이 됐습니다.
- 이름 사전은 작품 이름 112개뿐이라 "타노스", "인피니티 스톤", "바키" 같은 인물 · 물건 이름은 못 바꿉니다.
- → **영문화는 선택이 아니라 기본 단계로 넣어야 합니다.** (회의록 11/24의 "한글 질의 영문화 → 벡터 검색"과 같은 결론)

### ② 청크를 줄이기만 하면 토큰은 줄지만 답을 더 자주 포기한다 (R0-en → R1-en)
- 좋은 점: 상위 5개 맥락이 **14,864자 → 3,113자(-79%)**, 입력 토큰 **3,674 → 1,111(-70%)**.
- 나쁜 점: 정답 섹션은 비슷하게 찾지만(섹션 Hit 0.579 → 0.632), **정확한 문단까지는 덜 가져옵니다**(발췌 Hit 0.579 → 0.421). 그래서 **거절이 7 → 10문항**으로 늘고, 정답 충족은 4 → 3문항입니다.
- 이유: R0는 영화 줄거리 전체가 청크 하나라, 섹션을 맞히면 그 안의 모든 문단이 공짜로 따라옵니다. R1은 같은 섹션의 800자 조각 하나만 오니 필요한 문단이 빠질 수 있습니다.
- 응답 시간은 거의 같습니다(생성 시간이 대부분이라 입력이 줄어도 크게 안 변함).
- → **"작게 자르기"만으로는 도입 이유가 약합니다.** 작게 자른다면 상위 k를 5 → 10으로 늘리거나 앞뒤 조각을 함께 넣는 방법을 같이 봐야 합니다.

### ③ 인물 · 세계관 문서를 넣으면 정답이 두 배가 된다 (R1-en → R2-en)
- 정답 섹션이 색인에 있는 문항이 **13 → 19**가 됐고, 섹션 Hit@5 **0.632 → 0.842**, 정답 충족 **3 → 6문항**입니다.
- 새로 맞힌 문항: Q001(타임 스톤), Q009(윈터 솔저), Q015(젠데이아 역), Q002 · Q003(인피니티 스톤). 모두 근거가 세계관 · 인물 문서에 있는 문항입니다.
- 토큰 · 시간은 그대로입니다(청크 크기가 같아서).
- **대신 줄거리 문항은 손해를 봅니다.** 줄거리에만 근거가 있는 6문항에서 발췌 재현율이 **0.403 → 0.111**로 떨어졌습니다. 인물 문서 biography가 영화 줄거리를 다시 요약한 글이라, 줄거리 청크 자리를 인물 청크가 차지합니다(Q041 토르는 토르 인물 문서만 5개가 올라옴).
- Q004(와칸다)는 조금 다릅니다. R2는 세계관 문서의 **"와칸다" 섹션을 정확히 찾았지만**, 평가셋 근거가 블랙 팬서 줄거리로만 적혀 있어 점수상 실패로 잡혔습니다. 답변도 "아프리카 · 비브라늄 · 블랙 팬서" 핵심 사실을 빠뜨려 오답 판정을 받았습니다. 평가셋 근거에 세계관 문서를 추가할지 명석님과 정할 일입니다.
- R2에서 정답 섹션을 못 찾은 것으로 채점된 3문항(Q004 · Q011 · Q041)에 하이브리드(BM25 + 벡터, RRF)를 예시로 계산해 봤지만, 평가셋의 정답 섹션이 상위 5개에 들어오지 않았습니다. 이 중 Q004는 위처럼 관련 섹션을 이미 찾은 경우입니다. B 구성의 효과는 따로 돌려 봐야 압니다.
- → **인물 · 세계관 문서는 넣는 게 맞습니다.** 다만 줄거리 질문에서 밀리지 않게 문서 종류로 나눠 검색하거나, BM25(B 구성)로 작품 이름을 잡아 주는 보완이 필요해 보입니다.

### ④ 팀에 같이 정할 것
- **"인물 문서를 색인에 넣을지"** (#11 리뷰에서 나온 질문): 숫자로는 넣는 쪽이 낫습니다. 넣으려면 doc_id 규칙(`wp-{pageid}` 같은 것)이 필요합니다.
- 작품 문서의 **lead 섹션**은 R0 · R1 · R2 모두 색인에 없습니다. Q004 · Q056은 근거 일부가 lead라서, 넣으면 더 오를 수 있습니다.

## 2-5. 한계 · 주의

- **문항이 19개라 1문항 = 0.053입니다.** R0-en과 R1-en의 정답 충족 차이(4 vs 3문항)는 우연일 수 있습니다. 검색 지표(Hit, 재현율)는 임베딩이 거의 고정이라 상대적으로 믿을 만하고, 정답 충족은 생성 · 채점이 한 번씩이라 흔들릴 수 있습니다.
- **정답 충족은 LLM 판정(gpt-6-luna, j1)이고 사람이 검토하지 않았습니다.** 발제 기준대로 최종 평가 전에 사람 검토가 필요합니다.
- **채점 규칙 두 가지를 정했습니다.**
  - 답변 가능 문항에서 **거절한 답은 정답이 아닙니다.** R2의 Q049는 "찾을 수 없습니다"라고 거절하면서 사실 일부를 적어서 채점자가 맞다고 했지만, 거절로 처리했습니다.
  - 발췌 확인 조각 중 **원문 5곳 넘게 나오는 상투 문장은 뺐습니다.** Q016의 "…(MCU) media franchise, based on the Marvel…"가 인물 문서 20곳의 첫 문장이라, 그대로 두면 아무 인물 문서나 걸려도 맞은 것으로 셉니다.
- **정답 섹션을 못 찾았는데 맞힌 문항이 있습니다.**
  - Q007(로키 · 토르): 토르 영화 줄거리에도 "로키는 입양됐다"가 있어 정당한 정답입니다. 평가셋 근거 목록에 줄거리도 추가하면 좋겠습니다.
  - Q016(톰 홀랜드): 인용한 스파이더맨 줄거리에는 배우 이름이 거의 없어서 **모델이 원래 알던 지식**으로 답했을 가능성이 있습니다.
- 평가셋이 `problem.md`의 30문항(dev 10 / test 20, 근거 없음 3)이 아니라 20문항(근거 없음 1)입니다. 근거 없음 대응은 1문항으로만 봤습니다.
- B(BM25) · C(재정렬) · 리라이트 비교 · D(가공 색인)는 이번에 안 했습니다.

python -m experiments.chunking.run translate-team --date 2026-11-25 --trick # 함정 문항 3개
python -m experiments.chunking.run run S2 --max-chars 800 --overlap --date 2026-11-25 --trick \
