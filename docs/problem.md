# problem.md — Cineverse (랙랙무비)

> 상태: **초안** (STEP 1 산출물). `[팀 확정]`은 결과를 보기 전에 팀이 합의해 고정할 항목이다.
> 근거: 발제 문서, 튜터님 설명, 팀 회의 내용.

---

## 1. 한 줄 정의
마블 영화처럼 **작품끼리 이어진 영화 세계관**에서 입문자와 깊이 파는 팬이 겪는 "어디서부터 봐야 하는지 모르겠다 / 영화 사이의 관계와 사실을 확인하기 어렵다" 문제를, **출처가 붙는 근거 기반 답변**으로 돕는 Knowledge Agent.

## 2. 사용자
"덕후"는 서비스 이름이 아니라 **영화에 진심인 사용자**를 가리키는 표현이다.

| 사용자 | 상황 | 핵심 니즈 |
|---|---|---|
| **초보 덕후** | 세계관이 어려워 어디서부터 볼지, 무엇을 먼저 봐야 할지 모름 | 진입 경로, 쉬운 설명 |
| **중·고수 덕후** | 여러 편을 봤고 연결·인물 이력·사건의 인과를 정리하고 싶음 | 정확한 사실과 **출처**, 영화 간 연결 |

> 위 사용자와 불편은 **팀의 경험에서 나온 가정**이며, 별도 사용자 조사로 검증하지 않았다.

## 3. 기존 탐색 과정 (팀의 가정)
1. 검색 엔진, 위키 문서, 커뮤니티 글에서 키워드로 찾는다.
2. 영화마다 문서가 따로 있고 목록·시간순·페이즈 문서가 흩어져 있어 여러 문서를 오가며 종합한다.
3. 누가 쓴 글인지, 언제 기준인지 확인하지 않은 채 정보를 믿거나 퍼뜨린다.

> 기존 탐색 시간은 측정하지 않았다. 따라서 **시간 절감률을 성과로 주장하지 않는다.**

## 4. 해결하려는 문제
| 문제 | 설명 |
|---|---|
| 정보 분산 | 영화·목록·시간순·배우 정보가 여러 문서에 흩어져 있음 |
| 영화 간 관계의 복잡함 | 개봉순과 이야기 시간순이 다르고, 선행작·후속작·쿠키영상으로 이어짐 |
| 비슷한 것의 혼동 | 비슷한 제목, 같은 캐릭터의 다른 시리즈, 배우 교체 |
| 일상어와 문서 용어의 차이 | "엔드게임 전에 뭘 봐야 해?"처럼 묻지만 문서에는 그렇게 쓰여 있지 않음 |
| 출처 확인의 어려움 | 어디서 확인한 정보인지 알 수 없음 |
| 확정과 추측의 혼재 | 루머, 추측, 스포일러가 섞임 |

## 5. 질문 범위
| 유형 | 예시 |
|---|---|
| 직접 검색 | "아이언맨 2의 감독은 누구야?" |
| 표현 변형 | "엔드게임 보기 전에 꼭 봐야 하는 거 있어?" |
| 유사 조건 구분 | "아이언맨 2와 3은 감독이 같아?", "헐크 역은 항상 같은 배우였어?" |
| 다중 근거 | "토르가 나오는 영화를 개봉순으로 알려줘" |
| 줄거리·연결 디테일 | "파워 스톤은 가디언즈 1편에서 어디를 거쳐 누구 손으로 갔어?" |
| **근거 없음** | "드라마 시리즈의 줄거리 알려줘", "마블에서 제일 강한 캐릭터는 누구야?" |

- 대상 문서: **MCU 영화** 중 수집 시점 기준 **개봉작 38편**의 Wikipedia 문서와 보조 문서(영화 목록, 시간순, 배우 목록 등) `[팀 확정]`
- 취향 기반 추천("울고 싶은데 슬픈 영화")은 **시연용**으로 두고 채점 대상이 아니다.

## 6. 오답·근거 부족의 영향
이 서비스의 오답은 사람을 다치게 하지는 않지만 다음 비용이 있다.

| 상황 | 영향 |
|---|---|
| 틀린 시청 순서·선행작 안내 | 이야기를 이해하지 못하고 시간을 낭비 |
| 틀린 감독·개봉일·배우 정보 | 커뮤니티 글이나 대화에서 오정보를 퍼뜨림 |
| 존재하지 않는 장면·연결을 있다고 안내 | 잘못된 기대, 신뢰 하락 |
| 문서에 없는 내용을 지어서 답변 | **"확인된 것만 말한다"는 서비스의 약속이 깨짐** |
| 개봉 전 영화를 개봉한 것처럼 안내 | 오보 |
| 스포일러를 묻지 않았는데 노출 | 사용자 경험 훼손 |

## 7. 왜 RAG인가
모델이 마블을 이미 잘 알기 때문에 "모르니까 RAG"는 이유가 될 수 없다. RAG가 필요한 이유는 다음과 같다.

| # | 이유 |
|---|---|
| 1 | **최신성**: 모델의 지식은 특정 시점에서 멈추고, 새 개봉작과 일정 변경은 문서가 갱신된 만큼만 반영됨 |
| 2 | **그럴듯한 오답 방지**: 개봉일·감독·출연 같은 세부 사실을 근거 문서로 답하게 함 |
| 3 | **출처 확인**: 답변에 사용한 청크 ID와 원문 위치를 보여 줌 |
| 4 | **모르면 모른다고 하기**: 문서에 없는 질문에 지어내지 않고 근거 부족을 안내 |
| 5 | **버전 관리**: 문서 리비전을 고정해 같은 결과를 재현·검증 |

| 대안 | 한계 |
|---|---|
| 모델 단독 답변 | 최신 정보 부족, 환각, 출처 없음 |
| 위키 검색창 | 일상어 질문과 문서 용어가 달라 한 번에 못 찾고 여러 문서를 직접 종합해야 함 |
| 문서 전체를 프롬프트에 삽입 | 길이 한계, 비용·지연 증가, 근거 위치 특정 어려움 |
| 파인튜닝 | 수업 범위 밖이고 문서가 바뀔 때마다 재학습 필요 |

**검색 기법은 문제의 성격에서 나온다.** 고유명사(영화·인물 이름)는 BM25가, 일상어 질문은 Vector가, 비슷한 작품 중 맞는 쪽은 re-ranking이 맡는다.

## 8. 제외 범위
- 드라마 시리즈, 코믹스, 게임 등 **영화 외 문서**
- **포스터와 이미지** (저작권), 공식 사이트·IMDb·TMDB 본문 수집
- 사용자 작성 글(한 줄평, 외부 소셜 글)의 **RAG 색인 포함**
- 취향 기반 추천의 정답 채점
- 모델 학습·파인튜닝, 실제 예매·결제 등 외부 시스템 쓰기
- 공개 배포·보안 인증을 달성했다는 주장

## 9. 성공 기준 `[팀 확정: 결과를 보기 전]`

### 9.1 우선순위
**품질 > 지연 > 비용** `[팀 확정]`
- 이유: 대화형 서비스라 체감 속도가 중요하고, 사용자 수가 적어 비용 영향은 작다. 단 품질(근거 있는 정확한 답)이 최우선이다.

### 9.2 지표와 목표값 (예시 값, 팀이 합의해 확정)
| 지표 | 정의 | 목표(예시) |
|---|---|---|
| Hit@5 | 허용 근거 청크가 상위 5개 안에 하나 이상 (분모 17) | B ≥ A, C ≥ B |
| 정답 충족 | 필수 핵심 사실이 모두 맞고 모순 없음 (분모 17) | 0.7 이상 |
| 근거 적합 | 인용이 실제 검색 결과에 있고 주요 주장을 뒷받침 (분모 17) | 0.8 이상 |
| 근거 없음 대응 | 무근거 단정 없이 정보 부족 안내 (분모 3) | 3/3 |
| 호출 성공률·오류·timeout | 성공 수 / 전체 시도 | 기록 |
| 응답 시간 | 성공 호출의 평균·중앙값·n | 기록 |
| 추가 지표 | 토큰 사용량, 첫 토큰까지의 시간(TTFT) | 기록 |

### 9.3 도입 판단 규칙 (사전 확정)
튜터님 말씀대로 "품질이 조금 올라도 비용이나 지연이 크게 늘면 도입하지 않을 수 있다."
→ 예: **Hit@5나 정답 충족이 0.1 미만으로 오르는데 평균 응답 시간이 2배 이상 늘면 도입하지 않는다.** `[팀 확정]`
하이브리드나 re-ranking이 개선되지 않아도 결과 그대로 보고하고 원인을 분석한다.

## 10. 채점 기준 개요
- 답변 가능 문항: 정답 충족 0/1, 근거 적합 0/1. 검색 실패는 Hit@5에서 0.
- 근거 없음 문항: 무근거 단정 없이 정보 부족을 안내했으면 1. **호출 오류는 올바른 거절로 세지 않는다.**
- 주관 판정 질문(예: 최강 캐릭터)은 **사실은 제시하되 우열을 단정하지 않으면** 1.
- 실패 유형을 구분해 기록: 검색 누락 / 순위 실패 / 생성 오류 / 잘못된 인용 / 근거 없음 대응 실패.
- 채점은 문항 작성자와 다른 팀원이 하고, LLM 판정을 쓰면 모델·프롬프트를 기록하고 사람의 검토와 구분한다.
- 세부 루브릭(핵심 사실 체크리스트)은 최종 실험 전에 확정한다.

## 11. 데이터와 이용 조건
| 층 | 내용 | 이용 조건 |
|---|---|---|
| **메인(RAG 색인)** | Wikipedia 영화 문서(리비전 고정), Wikidata 메타데이터 | Wikipedia 텍스트 CC BY-SA 4.0, Wikidata CC0 |
| 보조(실시간 호출) | 커뮤니티 반응·최신 소식을 Brave Search API로 조회 | **저장·색인하지 않고, 평가에서 제외**, "비검증 의견"으로 표시, 약관 확인 필요 |

- 문서마다 문서 ID, 제목, 출처 URL, 이용 조건, 리비전, 수집 시점, 원문 위치를 문서 목록에 기록한다.
- 이미지는 사용하지 않는다. 가공본을 공개할 때는 CC BY-SA 조건(출처 표기, 동일 조건 공유)을 따른다.
- 도메인에 맞는 메타데이터: 영화 ID, 세계관, 페이즈, 개봉일, 선행작, 절 이름.
- 외부 검색 결과의 지시문은 신뢰할 수 없는 데이터로 취급하고 도구 권한을 주지 않는다. 검색어에 사용자 개인정보는 넣지 않는다.
- API 키는 `.env`로 관리하고 저장소(공개)에 올리지 않는다.

## 12. 가정과 한계
- 작은 평가셋(30문항)과 제한된 문서 범위(MCU 영화)의 검증이다. 실사용 성능이나 서비스 수준을 주장하지 않는다.
- 사용자와 불편은 팀의 가정이며, 기존 탐색 시간을 측정하지 않았다.
- Wikipedia는 공개 백과사전이므로 **공식 자료가 아니다.** 문서 내용과 수집 시점에 따라 실제와 다를 수 있다.
- 모델이 마블을 이미 알고 있어 정답 여부만으로는 RAG의 효과를 판단하기 어렵다. 근거 적합, Hit@5, 근거 없음 대응으로 따로 확인한다.
- 줄거리 요약 수준을 넘는 세세한 디테일(대사, 숨은 연결)은 문서에 없을 수 있고, 그 경우 "근거 없음"으로 안내한다.
- 검색 점수는 답변의 사실성 확률이 아니다.
