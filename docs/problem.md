## 1. 한 줄 정의

마블 영화처럼 **작품끼리 이어진 영화 세계관**에서 입문자와 깊이 파는 팬이 겪는 "어디서부터 봐야 하는지 모르겠다 / 영화 사이의 관계와 사실을 확인하기 어렵다" 문제를, **출처가 붙는 근거 기반 답변**으로 돕는 Knowledge Agent.

## 2. 사용자

"덕후"는 서비스 이름이 아니라 **영화에 진심인 사용자**를 가리키는 표현이다. 주 타깃은 중·고수 덕후이고, 초보 덕후에게는 세계관과 관람 순서 안내를 준다.

| 사용자 | 상황 | 핵심 니즈 |
|---|---|---|
| **초보 덕후** | 세계관이 어려워 어디서부터 볼지, 무엇을 먼저 봐야 할지 모름 | 진입 경로, 쉬운 설명 |
| **중·고수 덕후** (주 타깃) | 여러 편을 봤고 연결·인물 이력·사건의 인과를 정리하고 싶음 | 정확한 사실과 **출처**, 영화 간 연결 |

## 3. 기존 탐색 과정 (팀의 가정)

1. 검색 엔진, 위키 문서, 커뮤니티 글에서 키워드로 찾는다.
2. 영화마다 문서가 따로 있고 목록·시간순·페이즈 문서가 흩어져 있어 여러 문서를 오가며 종합한다.
3. 누가 쓴 글인지, 언제 기준인지 확인하지 않은 채 정보를 믿거나 퍼뜨린다.

> 기존 탐색 시간은 측정하지 않았다. 따라서 **시간 절감률을 성과로 주장하지 않는다.**

## 5. 질문 범위

답하는 범위는 **사실 · 연결 · 관람 순서**다. `[팀 확정]`

| 유형 | 예시 |
|---|---|
| 직접 검색 | "아이언맨 1편 쿠키 영상에 누가 나와?", "엔드게임 다음 개봉작이 뭐야?" |
| 표현 변형 | "엔드게임 보기 전에 꼭 봐야 하는 거 있어?" |
| 유사 조건 구분 | "헐크 역은 항상 같은 배우였어?", "2007년 닥터 스트레인지도 MCU야?" |
| 다중 근거 | "로키 드라마는 영화 어디와 이어져?" |
| 줄거리·연결 디테일 | "파워 스톤은 가디언즈 1편에서 어디를 거쳐 누구 손으로 갔어?" |
| **근거 없음** | "둠스데이 결말이 뭐야?"(미개봉), "데어데블 시즌 2 줄거리 알려줘"(2차 범위), "마블에서 제일 강한 캐릭터는 누구야?"(주관 판정) |

- **대상 문서 〔바뀜〕**: **영어 Wikipedia** 문서를 팀 데이터 모델에 맞춰 묶은 공통 데이터셋 `cineverse-dataset-schema`(문서 850개) 가운데 **134문서**를 색인한다 — 정식 · 개봉 · 1차 범위 작품 문서 68 + MCU 인물 문서 63 + 세계관 문서 3. `[팀 확정]`
  - 처음 계획은 MCU 팬덤 위키의 작품 문서였다. **이유**: 팬덤 위키는 약관 확인 전이라 본문을 받지 않았고(보류 — 데이터셋에는 작품별 팬덤 위키 문서 제목만 들어 있다), 같은 범위를 판 번호째 받아 둔 Wikipedia 묶음이 팀 모델로 바로 읽혔다. 1차 범위 71편이라는 선은 그대로 쓰되, Wikipedia 문서가 따로 없는 작품(원샷 · 단편 일부)은 카드만 들어간다.
- **넣는 절 〔바뀜〕**: 작품 문서의 첫머리(소개)와 Plot 절, 시리즈 문서의 회차 요약, 인물 문서의 소개와 **작중 서사**, 세계관 문서(인피니티 스톤 같은 사물 · 조직 · 타임라인)의 본문. 처음 계획은 "두 편 이상 나온 인물의 소개 문단만"이었다. **이유**: 팀 20문항의 정답 근거 55건 중 11건이 인물 서사 · 세계관 절에 있어, 이 절을 빼면 그 문항은 처음부터 찾을 수 없었다 (청크 종류 `biography` · `lore` 추가, PR #16).
- 정식이 아닌 작품과 미개봉작은 본문 없이 **한 줄 작품 카드**만 넣는다 (작품 표 159행 전부). 물으면 "MCU 정식 작품이 아니다" · "아직 개봉 전이다"를 카드로 답한다.
- 취향 기반 추천("가오갤 좋아하면 다음에 뭐 봐?")은 만들지 않았다 (§9.5 의 첫 번째로 잘랐다). 채점 대상도 아니다.

## 6. 오답·근거 부족의 영향

이 서비스의 오답은 사람을 다치게 하지는 않지만 다음 비용이 있다.

| 상황 | 영향 |
|---|---|
| 틀린 시청 순서·선행작 안내 | 이야기를 이해하지 못하고 시간을 낭비 |
| 틀린 감독·개봉일·배우 정보 | 커뮤니티 글이나 대화에서 오정보를 퍼뜨림 |
| 존재하지 않는 장면·연결을 있다고 안내 | 잘못된 기대, 신뢰 하락 |
| 문서에 없는 내용을 지어서 답변 | **"확인된 것만 말한다"는 서비스의 약속이 깨짐** |
| 개봉 전 영화를 개봉한 것처럼 안내 | 오보 |
| 스포일러를 묻지 않았는데 노출 | 사용자 경험 훼손 |

틀린 관람 순서와 지어낸 연결은 팬이 가장 빨리 알아채는 오류다. 그래서 **모르는 것은 모른다고 답하는 쪽을 오답보다 낫게 본다.**

## 7. 왜 RAG인가

모델이 마블을 이미 잘 알기 때문에 "모르니까 RAG"는 이유가 될 수 없다. RAG가 필요한 이유는 다음과 같다.

| # | 이유 |
|---|---|
| 1 | **최신성**: 모델의 지식은 특정 시점에서 멈추고, 새 개봉작과 일정 변경은 문서가 갱신된 만큼만 반영됨 |
| 2 | **그럴듯한 오답 방지**: 개봉일·감독·출연 같은 세부 사실을 근거 문서로 답하게 함 |
| 3 | **출처 확인**: 답변에 사용한 청크 ID와 원문 위치를 보여 줌 |
| 4 | **모르면 모른다고 하기**: 문서에 없는 질문에 지어내지 않고 근거 부족을 안내 |
| 5 | **버전 관리**: 위키 문서의 판 번호를 고정해 같은 결과를 재현·검증 |

| 대안 | 한계 |
|---|---|
| 모델 단독 답변 | 최신 정보 부족, 환각, 출처 없음 |
| 위키 검색창 | 일상어 질문과 문서 용어가 달라 한 번에 못 찾고 여러 문서를 직접 종합해야 함 |
| 문서 전체를 프롬프트에 삽입 | 길이 한계, 비용·지연 증가, 근거 위치 특정 어려움 |
| 파인튜닝 | 수업 범위 밖이고 문서가 바뀔 때마다 재학습 필요 |

**검색 기법은 문제의 성격에서 나온다.** 고유명사(영화·인물 이름)는 BM25가, 일상어 질문은 Vector가, 비슷한 작품 중 맞는 쪽은 re-ranking이 맡는다.

> **실측이 덧붙인 것 (dev 11문항)**: 위 역할 분담은 **질문과 문서의 언어가 같을 때** 성립했다. 문서가 영어라 한국어 질문 그대로는 BM25 가 걸리는 낱말이 거의 없었고(별칭이 없는 질문은 영어 토큰이 0개) 벡터도 정답을 후보에 잘 올리지 못했다. 그래서 세 기법의 비교보다 먼저 **질문을 영어 검색어로 바꾸는 일**이 필요했다 (§9.2).

## 8. 제외 범위

- **넷플릭스 계열 13개 시즌**(데어데블·제시카 존스·루크 케이지·아이언 피스트·디펜더스·퍼니셔)의 본문 — 작품 행만 등록하고 색인은 발표 뒤 2차로 미룬다 (문서는 공통 데이터셋에 들어 있다)
- **개별 에피소드 문서**(194개)와 작품 문서의 출연진 · 제작 · 개봉 · 평가 절 — 회차 내용은 시리즈 문서의 회차 요약으로만 들어간다
- MCU 정식 작품이 아닌 것의 본문, **미개봉작의 줄거리**, 코믹스·게임
- **수집 데이터의 포스터와 이미지** (저작권) — 색인과 API 응답에 이미지가 없다. 화면(`web/public` · `apps/streamlit/assets`)에는 팀이 넣은 로고와 일러스트 파일이 있는데, **이 파일들의 출처 · 이용 조건 기록은 저장소에 없다 (확인 필요)**
- 공식 사이트(Marvel.com · Disney+)와 IMDb의 **본문 수집** — 공식 사이트에서는 순서 값 · URL · 기준일만 적고, IMDb 가공본은 작품 표의 밑판으로만 쓴다. IMDb 값이 든 데이터셋은 저장소에 올리지 않는다 (§12 의 사고 기록 참고)
- **팬덤 위키 본문 수집** — 약관 확인 전이라 보류 〔바뀜 — 처음에는 메인 출처였다〕
- 사용자 작성 글의 **RAG 색인 포함** — 화면에 게시판(글 · 댓글 · 투표)이 생겼지만 〔추가〕 게시판 글은 색인하지 않고 검색 근거로도 쓰지 않는다
- 웹 검색 결과를 **고정 문서 색인에 섞는 것**과 검색된 페이지의 본문 수집 — 웹 결과는 제목 · URL · 요약 스니펫만 받아 별도 컬렉션에 넣는다
- 캐릭터 말투로 대화하는 기능 — 화면의 챗봇 이름이 "로어 AI 그루트"이지만 답변 본문은 근거 기반 답 그대로다. 취향 기반 추천도 없다
- **이전 대화를 기억하는 대화** — 챗봇은 질문 하나씩 답한다
- **D 구성(LLM 가공 색인)** 〔바뀜 — 비교 구성에서 제외, §9.2〕
- 모델 학습·파인튜닝, 실제 예매·결제 등 외부 시스템 쓰기
- 공개 배포·보안 인증을 달성했다는 주장 — 배포 설정(`docs/deploy.md`)과 횟수 제한은 만들었지만 서비스 수준을 주장하지 않는다

## 9. 성공 기준 `[팀 확정: 결과를 보기 전]`

### 9.1 우선순위

**품질 > 지연 > 비용** `[팀 확정]`

- 이유: 대화형 서비스라 체감 속도가 중요하고, 사용자 수가 적어 비용 영향은 작다. 단 품질(근거 있는 정확한 답)이 최우선이다.

### 9.2 비교 구성 〔바뀜〕

| 구성 | 흐름 | 기록 값 (`trace.retrieval_mode`) |
|---|---|---|
| 공통 | 이름 사전 치환 — 질문 속 한국어 작품·인물 이름에 영어 정식 이름을 덧붙인다 (규칙 기반, LLM 없음) | — |
| A | 벡터 검색 | `vector` |
| B | + BM25 + RRF 결합 | `hybrid` |
| C | + 재정렬 (Cross-Encoder) | `hybrid_rerank` |
| A+ | 영문 리라이트 → A | `vector_rewrite` |
| B+ | 영문 리라이트 → B | `hybrid_rewrite` |
| C+ | 영문 리라이트 → C | `hybrid_rerank_rewrite` |

처음 계획과 달라진 것은 넷이다.

| 처음 계획 | 최종 | 이유 |
|---|---|---|
| 리라이트는 **C 에만** 더하는 필수 최적화 (C+리라이트) | **모든 구성에서 기본으로 켠다.** A · B · C 를 요청해도 A+ · B+ · C+ 로 돌고 기록에는 실제로 돈 구성이 남는다. 끄는 것은 비교 실험용 `--no-rewrite` 뿐 (2026-11-26 팀 합의, PR #42) | 문서가 영어라 한국어 질문 그대로는 정답이 후보에도 잘 오르지 않았다. dev 실측: 리라이트 없음 Hit@5 A 2 · B 1 · C 2 /10 → 있음 A+ 6 · B+ 5 · C+ 5 /10. 리라이트 없는 A · B · C 는 검색 방식의 차이를 보기 전에 언어에서 막혔다 |
| A+ · B+ 구성 없음 | 재정렬 없는 리라이트 구성 **A+ · B+ 를 추가** (PR #26) | 리라이트의 효과와 재정렬의 효과를 따로 보려면 "리라이트만 더한 벡터 · 하이브리드"가 있어야 했다. 1차 실험에서 학용 · 서인의 가장 높은 점수가 리라이트 + 벡터 조합에서 나왔다 (조건은 서로 다르다) |
| D = C + LLM 가공 색인 | **만들지 않았다.** 구성 이름(`hybrid_rerank_enriched`)과 컬렉션 설정값만 남아 있고 고르면 오류가 난다 | §9.5 의 자르는 순서대로 뺐다. 서인의 1차 실험 코드 주석에 C 보다 낮았다고 적혀 있었고(수치는 남아 있지 않다), 원문 색인의 검색 문제가 먼저였다 |
| 모든 구성에 컨텍스트 **상위 5청크** | 검색 지표는 그대로 상위 5 로 재고, **생성 모델에는 상위 8개를 부모 문맥(부모당 최대 3,000자)으로** 넘긴다. 검색기마다 후보 40개, RRF 로 합친 목록은 자르지 않는다 (PR #43) | dev 실측: 재정렬 뒤 정답이 6위로 밀린 문항 3개, 후보 20 밖에 정답이 있던 문항 2개(RRF 17 · 25위), 정답 문장이 입력에 있는데 핵심 사실 하나가 빠져 오답인 문항 4개 |

- 모든 구성에 같은 생성 모델(`gpt-6-luna`) · 프롬프트(`p3-gather`) · 임베딩(`text-embedding-3-small`)을 쓴다.
- 평가를 돌릴 때는 웹 검색 흐름과 답변 캐시를 끄고 고정 문서 컬렉션만 읽는다. 웹 청크가 평가 색인에 섞이면 구성 간 비교와 근거 없음 문항의 채점이 깨진다.
- 발제가 요구한 A / B / C 비교는 리라이트를 끈 실행(①)으로 남아 있고, 리라이트를 켠 뒤의 비교는 A+ / B+ / C+ 다 (§9.3).

### 9.3 지표와 결과

**목표값은 확정 기록이 없다.** 아래 "목표(예시)" 는 처음 문서의 예시 값 그대로다. 분모도 달라졌다 〔바뀜〕 — 처음에는 최종 20문항(답변 가능 17 · 근거 없음 3)을 분모로 적었지만, **지금까지 돌린 것은 개발용 11문항(답변 가능 10 · 근거 없음 1)뿐**이라 아래 실측의 분모는 10 과 1 이다.

| 지표 | 정의 | 목표(예시) | dev 실측 — ④ 서인 PC (생성 8 · 후보 40 · 부모 문맥 · CUDA) |
|---|---|---|---|
| Hit@5 | 정답 청크가 상위 5개 안에 하나 이상 | B ≥ A, C ≥ B | A+ 6/10 · B+ 5/10 · C+ 7/10 |
| Hit@8 〔추가〕 | 생성에 넘기는 8개 안에 정답 청크 | — | A+ 7/10 · B+ 6/10 · C+ 10/10 |
| 정답 충족 | 필수 핵심 사실이 모두 맞고 모순 없음 (LLM 자동 채점) | 0.7 이상 | A+ 4/10 · B+ 3/10 · C+ 5/10 (사실 충족률 0.80 · 0.76 · 0.82) |
| 근거 적합 | 인용이 실제 검색 결과에 있고 정답 청크를 가리킴 | 0.8 이상 | 정답 청크 인용 A+ 5/10 · B+ 3/10 · C+ 6/10. 검색 결과 밖 인용은 답에 싣기 전에 버린다 |
| 근거 없음 대응 | 무근거 단정 없이 정보 부족 안내 | 3/3 | dev 는 1문항. 채점 기준 A+ 1/1 · B+ 1/1 · **C+ 0/1** |
| 호출 성공률·오류·timeout | 성공 수 / 전체 시도 | 기록 | 실행 기록(`results/*.jsonl`)의 `status` · `error` |
| 응답 시간 | 성공 호출의 중앙값 | 기록 | A+ 3.4초 · B+ 4.1초 · C+ 4.8초 |
| 추가 지표 | 토큰 사용량, 단계별 시간 | 기록 | 실행 기록의 `tokens` · `latency_ms`. 첫 토큰까지의 시간(TTFT)은 재지 않았다 (스트리밍 응답을 만들지 않았다) |

같은 11문항을 설정 · 기계를 바꿔 잰 값 (답변 가능 10문항, 자세한 표는 `docs/test_comparison/`):

| 실행 | 설정 (생성 수 · 후보 · 문맥) | 장치 | Hit@5 (A·B·C 계열) | 답 정답 | 응답 중앙값 |
|---|---|---|---|---|---|
| ① 리라이트 없음 | 5 · 20 · 청크 | CPU | A 2 · B 1 · C 2 | 1 · 0 · 1 | 1.9 · 2.5 · 13.8초 |
| ③ 리라이트 기본 | 5 · 20 · 청크 | CPU | A+ 6 · B+ 5 · C+ 5 | 4 · 2 · 3 | 3.7 · 3.7 · 15.9초 |
| M2 | 5 · 20 · 청크 | Apple GPU(mps) | A+ 6 · B+ 5 · C+ 5 | 4 · 3 · 3 | 3.0 · 3.4 · 6.7초 |
| ④ 설정 조정 뒤 | 8 · 40 · 부모 | NVIDIA GPU(cuda) | A+ 6 · B+ 5 · C+ 7 | 4 · 3 · 5 | 3.4 · 4.1 · 4.8초 |

이 결과로 말할 수 있는 것과 없는 것.

- **말할 수 있는 것**: 리라이트를 켜면 세 구성 모두 Hit@5 가 3~5문항 오른다. 재정렬 시간은 장치를 탄다 (후보 20 기준 CPU 12.1초 · mps 2.4초, CUDA 는 후보 58~76개에도 1.5초). 생성 · 번역 시간은 기계와 무관하게 1.4~2.0초다.
- **아직 말할 수 없는 것**: ④ 에서 C+ 가 오른 것이 설정 넷 중 무엇 때문인지 (한 번에 바뀌었다). B+ 가 A+ 보다 낮은 것이 경향인지 (11문항이라 1문항이 10%p 이고, 같은 조건에서도 답 정답이 ±1문항 흔들렸다). 예시 목표였던 "B ≥ A" 는 dev 에서 성립하지 않았다 — 결과 그대로 둔다.
- **목표에 못 미친 것**: 정답 충족은 가장 높은 실행이 5/10 으로 예시 목표 0.7 아래다. 근거 없음은 ④ C+ 가 "병원 이름은 확인할 수 없다" 뒤에 주변 사실을 덧붙여 채점에서 떨어졌다.
- **최종 20문항은 미실행이다.** `eval/test.json` 은 잠가 두었고, 최종 결과표(A/B/C 60건 + 최적화 비교)와 `report.md` 는 그 실행 뒤에 채운다.

### 9.4 도입 판단 규칙 (사전 확정)

튜터님 말씀대로 "품질이 조금 올라도 비용이나 지연이 크게 늘면 도입하지 않을 수 있다."
→ 예: **Hit@5나 정답 충족이 0.1 미만으로 오르는데 평균 응답 시간이 2배 이상 늘면 도입하지 않는다.** `[팀 확정]`
하이브리드나 re-ranking이 개선되지 않아도 결과 그대로 보고하고 원인을 분석한다.

dev 결과에 이 규칙을 대 보면 (11문항이라 판정이 아니라 방향이다):

| 후보 | 품질 변화 | 지연 변화 | 지금의 처리 |
|---|---|---|---|
| 영문 리라이트 | Hit@5 +0.3~0.4 | 응답 중앙값 A 1.9초 → A+ 3.4초. 이 실행은 저장한 검색어 파일을 써서 리라이트 호출 시간이 빠져 있다 — LLM 으로 리라이트하면 질문당 약 2.3초가 더 든다 | 도입 — 모든 구성 기본 |
| 재정렬, CPU | ③ 에서 B+ 대비 Hit@5 +0 · 답 +1문항 | 3.7초 → 15.9초 (약 4배) | 규칙대로면 도입하지 않는 쪽이다. 서버 설정으로 재정렬 없는 구성(`ASK_MODE=B+`)을 고를 수 있게 했다 |
| 재정렬, GPU + 설정 조정 | ④ 에서 B+ 대비 Hit@5 +2문항 · 답 +2문항 | 4.1초 → 4.8초 | 도입 — 챗봇 기본 구성 C+ |

장치에 따라 구성을 자동으로 바꾸는 코드는 없다. 재정렬 장치는 자동으로 고르지만(cuda → mps → cpu), 어떤 구성으로 답할지는 `ASK_MODE` 로 사람이 정한다 (M2 비교 문서 3절의 제안은 아직 반영 전).

### 9.5 일정이 밀리면 자르는 순서

① 취향 추천 → ② 웹 검색 경로 → ③ D 구성 → ④ 화면을 한 페이지짜리 최소 형태로. A · B · C와 C+리라이트 평가는 발제 필수라 자르지 않는다.

**실제로 잘린 것 〔결과〕**: ① 취향 추천과 ③ D 구성은 만들지 않았다. ② 웹 검색 경로는 만들었지만 서비스 기본값은 꺼짐이다 (`ASK_WEB=false`, `ask.py --web`). ④ 화면은 자르지 않았다 — Next.js 화면(홈 · 탐색 · 세계관 · 영화 정보 · 게시판 · 챗봇)과 발표용 Streamlit 화면을 둘 다 만들었다. 자르지 않기로 한 평가는 dev 11문항까지 했고 최종 20문항이 남았다.

## 10. 채점 기준 개요

- 답변 가능 문항: 정답 충족 0/1, 근거 적합 0/1. 검색 실패는 Hit@5에서 0.
- 근거 없음 문항: 무근거 단정 없이 정보 부족을 안내했으면 1. **호출 오류는 올바른 거절로 세지 않는다.**
- 작품 카드로 답한 경우: 카드가 질문의 답 자체면 정상 답변이다("2007년 닥터 스트레인지는 MCU야?" → 아니다). 카드가 문서가 없는 이유만 말해 주면 근거 없음이다("둠스데이 결말이 뭐야?" → 개봉 전).
- 주관 판정 질문(예: 최강 캐릭터)은 **사실은 제시하되 우열을 단정하지 않으면** 1.
- **실패 단계 〔바뀜 — 이름을 코드에 맞춤〕**: 호출 오류(`call_error`) / 검색 누락(`retrieval_miss`, 후보 안에 정답 없음) / 순위 밀림(`rank_drop`, 후보에는 있는데 상위 k 밖) / 근거 문장 누락(`evidence_sentence_missing`, 모델 입력에 정답 문장이 없음) / 생성 오류(`generation_error`, 근거는 읽었는데 인용 · 답이 틀림).
- **정답 키 〔바뀜〕**: 처음에는 정답 근거를 청크 ID(`작품 + 절 + 문단 번호`)로 적고, 번호가 밀리지 않게 문단 합치기 기준(150자)을 먼저 고정하기로 했다. 최종은 **정답을 원문 문장(발췌)으로 적고**, 청킹이 정해지면 그 발췌가 든 청크를 찾아 청크 ID 를 붙인다 (`src/evals/items.py` · `scripts/attach_chunks.py`). 정답 키에는 붙일 때의 색인 버전이 함께 남고, 지금 색인과 다르면 평가가 시작되지 않는다. **이유**: 청킹을 바꿀 때마다 번호가 밀려 정답 키가 깨졌고(민지 실험), 다섯 사람이 서로 다른 청킹을 시험하고 있었다.
- **채점 방식 〔바뀜〕**: 처음에는 "문항 작성자와 다른 팀원이 채점"이었다. 저장소에 남은 채점은 **LLM 자동 채점**이다 — 핵심 사실마다 충족(met) / 부분(partial) / 누락(missing)과 모순 여부를 판정한다 (`src/evals/judge.py`, 채점기 판 `j2`, 채점 모델은 생성 모델과 같은 `gpt-6-luna`). 채점기 자체를 먼저 검사한다 — 기준 답안은 통과하고 다른 문항의 답은 떨어져야 한다 (`judge_eval.py --calibrate`, 명석 PC 실행에서 10/10 · 0/10). **이유**: 구성 · 설정을 바꿔 가며 여러 번 돌리는 데 사람 채점이 따라갈 수 없었다. 사람이 다시 본 기록은 없으므로 "답 정답" 은 자동 판정 값으로 읽는다.
- 핵심 사실은 "빠지면 틀린 답"인 것만 문항당 4개 이하로 둔다. 함정 문항은 "전제를 바로잡았나"가 첫 번째 사실이다 (PR #22).
- 일부만 확인된 답은 상태를 바꾸지 않고(`answered`) `partial` 표시만 한다. 이것을 정답으로 볼지는 팀이 정하지 않았다 (§13).

- **청크의 본문은 위키 원문 그대로다.** 링크 · 각주 · 틀은 수집 단계에서 규칙으로 걷어냈고, 그때 함께 빠진 글자(항목 이름 · 소유격 · 띄어쓰기)는 같은 판의 원문에서 되살렸다. LLM 이 쓰거나 고친 글자는 없다.
- 수집 범위 분류(MCU 인가)와 IMDb 대응 판정은 에이전트가 했고, 사람이 확인한 레코드는 아직 없다.
- 도메인에 맞는 메타데이터: 작품 ID, 형식, 시즌, 연도, 타임라인 순번, 페이즈, 정식 작품 여부, 절 종류, 절 경로.
- 웹 검색 흐름 〔바뀜〕: 문서 검색 → 생성까지 해 본 뒤 **근거 없음으로 끝났을 때만** Brave 를 부른다 (처음 그림은 문서 컬렉션과 웹 컬렉션을 함께 먼저 보는 것이었다). 같은 질문으로 검색한 기록이 있으면 Brave 를 다시 부르지 않는다. 자세한 흐름은 `architecture.md` §6.
- 외부 검색 결과의 지시문은 신뢰할 수 없는 데이터로 취급하고 도구 권한을 주지 않는다. 검색어에 사용자 개인정보는 넣지 않는다.
- API 키는 `.env`로 관리하고 저장소(공개)에 올리지 않는다.

## 12. 가정과 한계

- **작은 평가셋과 제한된 문서 범위의 검증이다.** 공식 평가셋은 31문항(개발 11 · 최종 20)이고 지금까지의 수치는 개발 11문항뿐이다. 1문항이 10%p 이고, 같은 조건에서도 생성 · 채점 LLM 때문에 답 정답이 ±1문항 흔들렸다. 실사용 성능이나 서비스 수준을 주장하지 않는다.
- **최종 20문항 중 13문항은 누출 위험이 있다.** 다섯 사람이 1차 실험에서 설정을 고를 때 본 `question_set.jsonl` 문항이다. 최종 결과표에는 팀 밖에서 온 7문항의 점수를 따로 적는다 (`eval/README.md` · `report.md`).
- 사용자와 불편은 팀의 가정이며, 기존 탐색 시간을 측정하지 않았다.
- Wikipedia 는 누구나 편집하는 공개 백과사전이므로 **공식 자료가 아니다.** 문서 내용과 수집 시점에 따라 실제와 다를 수 있다. 정식 작품 여부와 순서만 공식 문서에 기댄다. 공통 데이터셋은 전 레코드가 검토 전이다.
- 색인은 영어 원문이다. 답변은 한국어로 쓰지만 화면의 근거 발췌는 영어로 보인다. 답은 영어 초안을 만든 뒤 한국어로 번역하므로, 번역에서 표현이 어긋날 수 있다 (이름 사전에 있는 이름과 청크 ID 는 번역 전에 가려 두었다가 되돌린다).
- 모델이 마블을 이미 알고 있어 정답 여부만으로는 RAG의 효과를 판단하기 어렵다. 근거 적합, Hit@5, 근거 없음 대응으로 따로 확인한다.
- 줄거리 요약 수준을 넘는 세세한 디테일(대사, 숨은 연결)은 문서에 없을 수 있고, 그 경우 "근거 없음"으로 안내한다.
- 선행작 후보는 출연진이 겹치는 정도로 계산한 **후보**이고, 쿠키영상 표시도 마지막 문단을 후보로 잡은 것이다. 둘 다 사람이 확인한 정답이 아니다.
- **부모 문맥은 근거 없음 답을 흐릴 수 있다.** 주변 본문을 더 읽으면서 "확인할 수 없다" 뒤에 관련 사실을 덧붙인 답이 나왔다 (④ C+, blind-q039).
- **재정렬 모델의 이용 조건을 확인하지 않았다.** `Dongjin-kr/ko-reranker` 는 임시값이고, 다른 다국어 모델과 같은 조건으로 견준 기록이 없다.
- 웹 검색 결과는 누가 썼는지, 맞는지 확인하지 않은 글이다. 적재해 두면 오래된 내용이 다시 쓰일 수 있다. 그래서 문서 근거보다 뒤에 두고 항상 "미검증"으로 표시하며, 검색 기록이 유효 기간(`WEB_STORE_TTL_DAYS`, 잠정 30일. 결과 0건은 `WEB_STORE_EMPTY_TTL_DAYS`, 1일)을 넘으면 다시 검색한다. 웹 검색 도구 단독(검색 · 적재 · 재사용)은 2026-11-25 에 실측했고, 서비스 경로(`ask.py --web` · `ASK_WEB`)에 이어 붙인 뒤의 실행 기록은 저장소에 없다.
- **데이터셋이 저장소에 한 번 올라갔다.** 2026-11-26 `.gitignore` 의 데이터 규칙이 주석 처리된 사이 데이터셋 파일이 dev 에 들어갔고, 같은 날 지운 뒤 규칙을 고쳤다 (PR #46 · #45). dev 의 지금 파일에는 없지만 **git 기록에는 남아 있다.** 기록을 정리할지(비공개 전환 또는 기록 재작성)는 팀이 정하지 않았다.
- 검색 점수는 답변의 사실성 확률이 아니다. 근거 부족을 유사도 임계값으로 판정하지 않는다 — 1차 실험에서 답이 없는 질문의 1위 유사도가 답이 있는 질문의 평균보다 높게 나왔다.
