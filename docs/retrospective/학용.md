## 잘한 점 (Keep)

- **재정렬 전 순위를 남겼다.** 재정렬하면 원래 순위가 사라져 검색 방식의 효과를 비교할 수 없으므로 `rank_before_rerank` 를 따로 보존했다. 어떤 문서가 얼마나 이동했는지 볼 수 있다.
- **모델 없이도 테스트가 돈다.** 재정렬 모델을 지연해서 불러오고, 실제 모델을 부르지 않는 테스트용 재정렬기로 점수 정렬 · 빈 후보 · 점수 개수 불일치 오류를 검증했다.
- **근거 밖 인용을 막았다.** LLM 이 검색 결과에 없는 문서를 인용할 수 있어, 허용된 출처만 최종 답변에 남기고 근거가 부족하면 억지로 답하지 않고 `NO_EVIDENCE` 로 처리했다.
- **캐시 키에 실행 조건을 담았다.** 질문만 키로 쓰면 설정이 바뀌어도 이전 결과가 재사용되므로 검색 모드 · 데이터셋 버전 · 임베딩 모델 · 프롬프트 버전을 함께 넣어, 조건이 바뀌면 자동으로 무효화되게 했다.
- **실패 원인을 추적할 수 있게 채점했다.** 평균 점수만 남기지 않고 질문 ID · 답변 상태 · 핵심 사실별 판정 · 사실 충족률 · 통과 여부 · contradiction 여부를 기록했다.
- **발표 화면을 기존 코드와 분리했다.** Streamlit 코드는 별도 폴더에 두고 공통 RAG 모듈을 읽어 쓰도록 해 Next.js · FastAPI 코드와 충돌하지 않게 했다.

## 아쉬운 점 (Problem)

- 처음에는 팀원들이 구현한 코드와 실험 결과를 이해하기 어려웠고, 어떤 작업이 실제 프로젝트에 필요한지 구분하기도 쉽지 않았다.
- import 정렬이나 사용하지 않는 import 처럼 작은 문제로도 CI 가 실패할 수 있다는 것을 겪고 나서야 알았다.
- 개인 실험 중 같은 `chunk_id` 가 다른 컬렉션에 있어 적재가 중단되는 안전 검사에 걸렸다. 팀 DB 와 개인 DB 를 처음부터 나눠 두지 않으면 다른 사람의 컬렉션에 영향을 줄 수 있었다.

## 다음에 해 볼 것 (Try)

- 검색 품질과 답변 품질을 처음부터 따로 평가하기.
- PR 을 올리기 전에 단위 테스트 · 전체 테스트 충돌 · formatter · linter · 환경변수와 비밀키 노출 · 의도하지 않은 파일 포함 여부를 확인하기.
- 개인 실험은 로컬 DB 와 별도 컬렉션에서 시작하고, `.env` 와 실제 데이터가 Git 에 올라가지 않게 관리하기.
- 답변 캐시는 개발 중 반복 실행을 줄이는 용도로만 쓰고, 공식 평가에는 캐시된 결과가 섞이지 않게 하기.

## 배운 것

- **기술: 검색이 좋아도 답이 좋은 건 아니다.** 검색된 문서가 있어도 답변에 근거가 제대로 반영되지 않을 수 있었고, 검색 점수가 높아도 실제 정답과 관련이 낮을 수 있었다. 검색 품질과 답변 품질은 따로 평가해야 하고, "모르는 내용을 모른다고 말하는 것" 도 RAG 의 중요한 기능이라는 것을 배웠다.
- **협업: 브랜치와 테스트로 구조를 익혔다.** 브랜치별 담당 기능을 나누고 각 기능의 테스트를 확인하면서 처음에는 낯설던 프로젝트 구조를 조금씩 이해할 수 있었다. 발표 화면을 만들면서는 기술적으로 동작하는 것뿐 아니라 검색 과정과 출처를 사용자가 이해하기 쉽게 보여주는 것도 중요하다는 것을 느꼈다.

## 한 줄 소감

RAG 는 모델 하나를 연결하는 작업이 아니라 데이터 · 검색 · 생성 · 평가 · 화면을 하나의 흐름으로 설계하는 작업이라는 것을 배웠다.
