## 잘한 점 (Keep)

- **실험 브랜치를 한 사람에 하나씩.** 같은 데이터 위에서 각자 다른 접근을 마음껏 시도하게 했고, 취합 회의에서 정말 다양한 방법이 나왔다.
- **기록 기준을 먼저 맞췄다.** 공통 로거와 평가 실행 기록기로 단계별 시간과 토큰을 같은 형식으로 남겨, 실험끼리 비교하고 느린 구간을 추적할 수 있었다. 같은 `run_id` 로 다시 돌려도 기존 결과를 덮어쓰지 않게 했다.
- **실제 사용자 질문에서 출발했다.** 마블을 잘 몰라서 스레드(Threads)에 직접 글을 올려 반응을 모았고, 실제 질문을 바탕으로 평가셋 후보 10개를 설계했다.
- **'근거 없음' 과 장애를 나눴다.** 검색 호출 실패를 근거 부족으로 집계하지 않도록 서비스 경로에서 상태와 실패 단계를 분리했다.

## 아쉬운 점 (Problem)

- 초반에 진행 병목이 있었고, 빠른 진행을 위해 업무 분담이 어느 정도 일방적이었다. 막판 최종 배포의 어려움도 다 커버하지 못했다.
- [#46](https://github.com/766min/ax-rag-cinema/pull/46) 에서 CUDA PyTorch 를 기본 의존성에 넣어 macOS 설치가 실패하고 CI 가 느려졌다. [#47](https://github.com/766min/ax-rag-cinema/pull/47) 에서 선택 설치로 분리해 바로잡았다.
- GPU 재실험에서는 장치와 검색 · 생성 설정(후보 풀 20 → 40, 생성 입력 5 → 8)이 함께 바뀌어, 점수와 시간 차이의 원인을 하나로 가릴 수 없었다.
- 웹 검색 보강이 실제로 어떤 질문에서 답변 품질을 높였는지 충분히 비교하지 못했다.

## 다음에 해 볼 것 (Try)

- 팀장을 다시 맡는다면 더 깊이 미리 공부해 업무 분담을 명확히 하고, 매일 진행 목표를 잡아 리딩하기.
- 비교 실험은 한 번에 한 변수만 바꾸고, 나머지는 같은 조건으로 다시 실행하기.
- 도구를 더하기 전에 줄이려는 실패를 먼저 정하고, 추가 전후의 답변 품질과 지연을 함께 비교하기.
- 의존성을 바꿀 때는 macOS · Windows · Linux 설치를 먼저 확인하고 올리기.
- 이번 코드를 종합적으로 리뷰하고, 팀원들과 추가 목표를 정해 디벨롭 이어가기.

## 배운 것

- **기술: 점수가 낮을 때 어디부터 볼지.** 청킹을 바꿔도 같은 문항이 계속 누락됐는데, 같은 색인(CK04)에서 질의만 영문으로 리라이트하자 답변 가능한 개발셋 8문항의 Hit@5 가 2/8 에서 7/8 로 올랐다. 검색 후보 순위, 모델이 실제로 읽은 문맥, 최종 인용을 따로 기록해야 검색 누락과 답변 실패를 구분할 수 있다는 걸 배웠다.
- **협업: 같은 데이터, 다른 시도.** 각자의 실험 결과를 나누면서 '번역' 이슈나 스키마 · 데이터 구축의 중요성처럼 혼자서는 지나쳤을 것들을 직접 체감했다. 서로 할 일이 더 없는지 계속 묻던 팀원들 덕분에 가능했다.
