# 평가셋 (eval/)

최종 코드에서 검색 · 답변 구성을 비교할 때 쓰는 **공식 평가셋 30문항**이다. 2026-11-26 확정.

| 파일 | 문항 | 쓰임 |
|---|---|---|
| `dev.json` | 10 | 설정값 조정용 (후보 수 · 가중치 · 근거 부족 판정 등). 여러 번 봐도 된다 |
| `test.json` | 20 (답변 가능 17 · 근거 없음 3) | 최종 결과표용. **잠근 뒤 고치지 않는다** (architecture.md §8) |

## 한 줄 요약

- 정답을 **청크 번호가 아니라 원문 문장(발췌)** 으로 적었다. 그래서 청킹 방식이 정해지지 않아도, 나중에 바뀌어도 그대로 쓴다.
- 청킹이 정해지면 `scripts/attach_chunks.py` 로 그 청킹의 청크 번호(`gold_chunk_ids`)를 붙여서 채점한다.

## 1. 어떻게 만들었나

### 1-1. 출처 네 곳을 하나로

| 출처 | 문항 | 공식 30문항에 들어간 수 |
|---|---|---|
| 루트 `question_set.jsonl` (팀 공식 20문항) | 20 | 20 (전부) |
| 민지 청킹 실험의 함정 문항 T001~T003 | 3 | 2 |
| 명석 실험 세트 (문서를 보지 않고 쓴 40 · 청크를 보고 쓴 60) | 100 | 8 |
| 배 · 정 평가셋 (B01~B10 · A01~A10) | 20 | 0 (추천 · 가치관 위주라 근거가 아직 없음) |

같은 사실을 묻는 문항 4개를 빼고 139문항이 남았다. 그중 30문항이 공식, 나머지 109문항은 확장 진단셋이다(아래 4절).

### 1-2. 세 축으로 분류

| 축 | 값 | 기준 |
|---|---|---|
| 근거위치 | 줄거리 · 시놉시스 · 인물 · 세계관·사물 · 메타 · 추천·가치관 · 문서에 없음 | 답이 있는 문서 종류와 절 |
| 난이도 | 초보 · 중수 · 고수 · 함정 | 초보 = 근거 1곳 · 작품 1개 / 중수 = 2곳 · 2개 (인과 · 시간선) / 고수 = 3곳 이상 · 3개 이상 (변화 추적) / 함정 = 잘못된 전제 · 일반화 · 문서에 없음 |
| 질문유형 | 사실 · 관계 · 인과 · 시간선 · 비교·가치관 · 추천 · 근거 검증 | 추천 · 비교·가치관은 `eval_track = answer_only` (검색 지표에서 뺌) |

### 1-3. 정답을 적는 방식

문항마다 세 가지를 적는다.

1. **정답 섹션**: 데이터셋 `sections.jsonl` 의 문서 · 절 (`doc_id` · `section_index` · `section_path`, 팀 문서 ID `team_doc_id` 도 함께)
2. **정답 문장**: 그 절 본문에서 그대로 복사한 원문 발췌. 스크립트로 본문에 실제로 있는지 확인했다
3. **채점 핵심 사실**: 답변 채점에 쓰는 사실 2~4개 (`/` 로 구분)

청크 번호를 적지 않은 이유는 민지 실험의 교훈 때문이다. 청킹을 바꾸면 번호가 밀려 정답 키가 깨진다.

### 1-4. 공식 30문항을 고른 기준

1. 팀 `question_set.jsonl` 20문항은 모두 넣었다. 팀이 이미 정답 섹션 · 발췌 · 핵심 사실을 검토했다.
2. 팀 20문항에 없는 칸을 10문항으로 채웠다: 시놉시스 2 · 에피소드 1 · 메타(감독) 1 · 인물 소개 1 · 인물 동기(인과) 1 · 함정 2 · 근거 없음 2.
3. 청크를 보고 쓴 질문보다 보지 않고 쓴 질문을 먼저 골랐다. 청크를 보고 쓰면 원문 표현이 질문에 섞여 점수가 부풀기 때문이다.
4. 팀 밖에서 고른 10문항은 한국어 기준 답 · 핵심 사실 · 원문 발췌를 원문을 보고 다시 적었다. `검토 메모` 에 "손으로 채움(검토 필요)" 이라고 표시해 두었으니 팀이 한 번 읽어 주면 좋다.
5. test 20 = 답변 가능 17 + 근거 없음 3 (architecture.md §8 의 발제 기준).

## 2. 칸 설명

루트 `question_set.jsonl` 의 칸을 순서 그대로 두고, 뒤에 칸을 더했다. JSON 배열이다.

| 칸 | 뜻 |
|---|---|
| `query_id` … `원문 근거 발췌` | 팀 `question_set.jsonl` 과 같은 9칸 (`EvalItem` 으로 읽는 방식도 같음 — `tests/shared/test_models.py`) |
| `근거위치` · `질문유형` · `eval_track` | 1-2절의 분류 |
| `variant_of` | 말투만 바꾼 변형이면 원본 ID (공식 30문항에는 없음) |
| `작성자` | team · minji · ohmseok |
| `전제 오류` | 함정 문항에서 무엇이 틀렸는지 한 줄. 전제를 바로잡았는지 따로 채점할 때 쓴다 |
| `경계 걸침` | 정답 발췌가 기준선 청킹(최대 800자 · 문장 경계 · 겹침 없음)에서 청크 두 개 이상에 걸치는가. 근거 없음 문항은 `null` |
| `필요 문서 수` | 근거에 적힌 서로 다른 문서 수. 근거 없음 문항은 0 |
| `근거` | 정답 섹션 + 정답 문장 목록 `{doc_id, team_doc_id, section_index, section_path, 발췌}` |
| `split` | `dev` · `test` |

## 3. 무엇을 검증하는 데 쓰나

### 쓸 수 있는 것

| 결과표 칸 (팀 인사이트 취합 2026-11-25) | 어떻게 재나 | 대상 |
|---|---|---|
| 정답 섹션 적중 (Hit@k) | `attach_chunks.py` 로 붙인 `gold_chunk_ids` 가 상위 k 개에 있는가 (`EvalItem.hit_at`) | 답변 가능 27 |
| 모델 입력에 정답 문장이 들어간 문항 수 | 모델에 넣은 문맥에 `근거[].발췌` 가 들어 있는가. 청크 번호 없이도 바로 잰다 (영문자 · 숫자만 남겨 비교) | 답변 가능 27 |
| 답변 핵심 사실 충족 | `채점 핵심 사실` 을 답변이 모두 담았는가 (LLM 판정 + 사람 확인) | 답변 가능 27 |
| 근거 없음 대응 | 근거가 없다고 안내했는가 (`answerable = false`) | test 3 (Q019 · blind-q037 · blind-q040) |
| 전제 바로잡기 | 틀린 전제를 바로잡았는가 (`전제 오류` 와 첫 핵심 사실) | 2 (minji-T001 · minji-T003) |

비교 단계별로 보면 좋은 문항 묶음:

- **부모 문맥 확장**: 다중 작품(`필요 문서 수` 2 이상) 10문항, 인물 서사 · 사건 흐름 문항
- **문장 겹침 (CK05 · CK09)**: `경계 걸침 = true` 9문항
- **A 벡터 → B +BM25 → C 재랭킹**: 전체. 난이도별로 나눠 보면 고수 · 다중 작품에서 차이가 커진다

### 쓰면 안 되는 것 (한계)

- **칸별 결론**: 30문항이라 1문항이 3.3%p, dev 는 10%p 다. "인물 질문에서 B 가 낫다" 같은 칸 단위 결론은 이 세트로 내지 않는다. 칸별 약점은 확장 진단셋으로 본다.
- **추천 · 가치관 답변**: 공식 30문항에는 없다 (근거가 없는 배 · 정 문항뿐이라서). 확장 진단셋에 `answer_only` 로만 있다.
- **dev 로 근거 부족 판정 맞추기**: dev 에 근거 없음 문항이 0개다. 근거 부족 기준값은 확장 진단셋의 근거 없음 문항으로 맞춰 본다.
- **영어 질문 경로**: 질문은 모두 한국어다. `question_en` 이 없어 영어 질문을 바로 넣는 비교는 안 된다(한국어 → 영어 변환을 거쳐야 한다).
- **웹 검색 경로 · 팬덤 위키 출처**: 근거는 모두 영어 Wikipedia(데이터셋 sections.jsonl)다. 웹 경로는 평가에서 끈다(§8).
- **관람등급 · 장르**: 데이터에 칸이 없어 묻지 않았다.

### 알아 둘 점

- 팀 문항 일부는 근거가 **인물 전기 절 · 세계관 문서**(팀 섹션 plot · synopsis · intro 밖)에 있다: Q001 · Q002 · Q007 · Q011 · Q040 · Q042 · Q045 · Q049. 이 절을 색인에 넣지 않는 청킹에서는 정답을 찾을 수 없고, 그게 그대로 점수에 나온다. 청킹을 비교할 때 "어느 절을 넣었나"도 함께 재는 셈이다.
- 팀 문항의 발췌는 원본 그대로 약 180자 구간이다(문장 중간에서 시작하거나 `…` 로 끝나기도 한다). 정답 위치를 가리키는 데는 충분하지만, `경계 걸침` 판정은 이 발췌 길이 기준이다.
- `필요 문서 수` 는 근거에 적힌 문서 수다. 같은 사실을 두 문서가 담은 경우(예: Q002 의 세계관 문서 + 인피니티 워 줄거리)는 실제로 하나만 읽어도 될 수 있다.
- Q019(근거 없음)에는 참고용 근거가 적혀 있다. `answerable = false` 라 정답 키(`gold_chunk_ids`)는 붙지 않는다.

## 4. 확장 진단셋 (공식 아님)

공식 30문항을 뺀 109문항은 확장 진단셋이다. 칸별 약점을 찾는 보조 자료라 점수를 결과표에 쓰지 않는다.

- 지금은 `tmp/eval_diag.json` (git 에 올라가지 않음). 109문항 중 108개는 핵심 사실이 비어 있고, 83개는 정답 문장을 자동으로 골라 사람 확인이 필요하다.
- 경계 걸침 · 다중 작품 문항이 아직 0개라 Codex 로 늘릴 계획이다. 프롬프트와 목표는 `docs/experiments/eval_set_codex_prompts.md`.
- 공식 문항과 같은 사실을 묻는 문항은 진단셋에 넣지 않는다 (test 누출 방지).

## 5. 쓰는 법

청킹 결과가 나오면 정답 청크 번호를 붙인다. `eval/` 원본은 그대로 두고 새 파일이 생긴다.

```powershell
uv run python scripts/attach_chunks.py --eval eval/test.json --chunks <청킹 결과>.jsonl --index-version <색인 버전> --out tmp/test_gold.json
```

- 청킹 결과는 한 줄에 청크 하나인 jsonl 이면 된다. 칸 이름이 다르면 `--id-field` · `--text-field` · `--doc-field` 로 알려 준다.
- 화면에 정답 발췌를 찾은 비율과 못 찾은 근거가 나온다. 못 찾은 검색 문항은 `gold_chunk_ids` 가 비어 `EvalItem.hit_at` 이 오류를 낸다 (조용히 0점이 섞이지 않게).
- 확인한 결과 (공식 30문항, 정답 발췌 62개): 기준선 청킹 100% · `tmp/chunks_dryrun.jsonl` 83.9% · 같은 절을 400자로 자른 청킹 83.9%. 못 찾은 것은 모두 그 청킹이 자르지 않은 절(인물 전기 · 세계관)이었다.

관련 스크립트:

| 스크립트 | 하는 일 |
|---|---|
| `scripts/build_eval_set.py` | 출처를 합쳐 분류 · 중복 제거 · 칸 계산, 공식 후보 · 진단셋 · 빈칸 표(`docs/experiments/eval_set_gaps.md`) 생성. `eval/` 은 쓰지 않는다 |
| `scripts/check_eval_gen.py` | Codex 가 만든 문항 검증 (발췌가 본문에 있는지, 칸 값, 중복 등) |
| `scripts/attach_chunks.py` | 청킹 결과에 꽂아 `gold_chunk_ids` 채우기 |
| `scripts/baseline_chunks.py` | 기준선 청킹(800자 · 문장 경계 · 겹침 없음). `경계 걸침` 판정에 쓴다 |

`build_eval_set.py` 를 다시 돌리려면 배 · 정 평가셋 md 와 명석 실험 세트(`tmp/`)가 필요하다. 둘 다 저장소에 없어서, 공식 30문항은 이 폴더의 파일이 원본이다.
